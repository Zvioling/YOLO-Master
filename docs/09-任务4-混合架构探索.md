## 目录

### 4.0 任务原文（Issue #54 原文）

> 混合架构探索：尝试将 MoT 与 MoE 进行层级组合（如 backbone 用 MoE、neck 用 MoT），或与 MoA 进行交叉组合，评估是否产生协同增益（mAP 提升 > 1% 或延迟降低 > 10% 视为有意义）

### 4.1 任务介绍

本任务探索 MoT 与 MoE/MoA 的层级组合，评估是否能产生协同增益。

| 架构组合 | 设计思路 | 评估标准 |
|---------|---------|---------|
| MoE(backbone) + MoT(neck) | 全局特征 + 局部细节 | mAP > 1% 或延迟 > 10% |
| MoT + MoA 交叉 | 浅层局部 + 深层全局 | 同上 |

**协同增益判定**：
- ✅ mAP 提升 > 1%（精度增益有意义）
- ✅ 延迟降低 > 10%（效率增益有意义）

### 4.1.1 方案 D 训练结论（已训练完成，实测 2026-08-01 标准 benchmark）

| 维度 | 实测结果 | 协同增益判定（> 10% 阈值） |
|------|----------|--------------|
| mAP50-95 | 16.80% (vs v08_mot 16.93%, -0.13%) | ❌ 精度增益不显著（损失极小，可接受） |
| mAP50 | 29.52% (vs v08_mot 29.77%, -0.25%) | ❌ 精度增益不显著 |
| **CPU 延迟** | **170.853ms (vs v08_mot 172.660ms, -1.05%)** | ❌ **与基线持平**（未达 10% 阈值） |
| **GPU 延迟** | **49.416ms (vs v08_mot 55.441ms, -10.84%)** | ✅ **延迟增益达标（> 10%）** |
| 参数 | 3.00M (vs v08_mot 3.71M, -19.1%) | ✅ **参数大幅优化** |
| 路由稳定 | moe_loss = 9.95e-05 | ✅ **完全稳定** |
| **总体判定** | **GPU 延迟 -10.84%（达标）+ 参数 -19.1%（大幅优化）+ CPU 延迟 -1.05%（持平）** | **架构创新成立**（按 Issue #54 "二选一"标准：GPU 达标即满足） |

**⚠️ 重要说明**：
- **GPU 延迟达标**（-10.84% > 10% 阈值），按 Issue #54 协同增益"二选一"标准已满足
- **CPU 延迟未达 10%**（仅 -1.05%，与 v08_mot 几乎持平），shared expert pool 在 CPU 上没有加速收益（CPU 受限于 kernel launch，不受显存访问影响）
- **GPU 提升机制**：shared expert pool 减少显存访问带宽，在 RTX 5060 Laptop GPU 上体现为 6.025ms（10.84%）的延迟下降，符合"参数共享 → 显存局部性提升 → GPU 加速"的理论预期
- **数据来源**：`experiments_zviolin/runs/latency_cpu_640.csv`（5 行）、`experiments_zviolin/runs/latency_cuda_0_640.csv`（5 行），均使用 warmup=500, reps=2000 标准测量

##### 方案 D：轻量型（Cross-Scale Expert Sharing — 跨尺度专家共享，**架构层创新**）

**设计目标**：在 v08_mot 基础上，**通过跨尺度共享 expert pool 实现真正的架构创新**，同时保持轻量化

**与 v08_mot 的关键差异**：

| 元素 | v08_mot | 方案 D (Shared) | 说明 |
|------|---------|--------|------|
| **backbone MoE 块** | 3 (独立 expert) | **2 (共享 expert)** | **-1，独立 expert → 共享 expert pool** |
| **Expert 总数** | 28 (4+8+16) | **4 (共享)** | **-86%** |
| head C2fMoT 块 | 3 | 3 | 保持 |
| head P3 | C3k2 | C3k2 | 保持 |
| **创新方式** | 块数调整 | **跨尺度 expert 共享** | **架构层创新** |
| 总层数 | 608 | ~520 | -88 |
| **总参数（实测）** | 3.71M | **3.01M** | **-19.1%** |
| **CPU 延迟（实测，2026-08-01 标准 benchmark）** | 172.660ms | **170.853ms** | **-1.05%** |
| **GPU 延迟（实测，2026-08-01 标准 benchmark）** | 55.441ms | **49.416ms** | **-10.84%**（达标 10% 阈值） |

**核心创新点**：

1. ⭐⭐⭐⭐⭐ **Cross-Scale Expert Pool Sharing**
   - P3 和 P4 共享同一组 4 个 experts（pool_id="p3_p4"）
   - 通过 class-level registry 自动复用 expert 参数
   - 验证"参数共享 vs 性能"的权衡

2. ⭐⭐⭐⭐ **跨尺度特征传递**
   - 浅层 P3 expert 可被中层 P4 复用
   - 通过共享 expert pool 自然实现浅层-中层特征交互
   - 减少 expert 数量，提升每个 expert 训练充分度

3. ⭐⭐⭐⭐ **轻量化设计**
   - P5 用 A2C2f 代替 MoE（去除 P5 MoE 块）
   - 总参数从 3.71M 降至 3.01M（**-19.1%**）
   - GPU 延迟从 55.441ms 降至 49.416ms（**-10.84%**，达标 10% 阈值）

4. ⭐⭐⭐ **训练稳定性**
   - 每个 expert 被多个尺度训练，特征更鲁棒
   - 避免 expert 数量过多导致路由学习困难

**YAML 设计原则**：
- backbone 用 `SharedExpertMoE` 替代 v08_mot 的 `LowRankHybridAdaptiveGateMoE`
- P3 和 P4 的 `SharedExpertMoE` 使用相同 `pool_id="p3_p4"`，自动共享 expert pool
- P5 用 A2C2f 代替 MoE（轻量化）
- head 沿用 v08_mot 的 3 个 C2fMoT

**YAML 文件路径**：`ultralytics/cfg/models/master/v0_8/det/yolo-master-moe-mot-shared-n.yaml`

**完整 YAML 内容**：

```yaml
# YOLO-Master v0.8 MoE+MoT Shared-Expert (方案 D) 🚀 AGPL-3.0 License
# 创新点: Cross-Scale Expert Sharing — P3 和 P4 共享同一 expert pool
# P5 不再使用独立 MoE, 用 A2C2f 代替 (轻量化)

nc: 80
scales:
  n: [0.50, 0.25, 1024]

backbone:
  - [-1, 1, Conv, [64, 3, 2]]            # 0-P1/2
  - [-1, 1, Conv, [128, 3, 2]]           # 1-P2/4
  - [-1, 2, C3k2, [256, False, 0.25]]    # 2

  - [-1, 1, Conv, [256, 3, 2]]           # 3-P3/8
  - [-1, 2, C3k2, [512, False, 0.25]]    # 4

  # P3 SharedExpertMoE (创建 expert pool "p3_p4")
  - [-1, 1, SharedExpertMoE, [512, 4, 2, 0.5, 8, 1.2, 0.5, 1.0, 1.0, 0.01, 8, 2, 0.5, "p3_p4"]]  # 5

  - [-1, 1, Conv, [512, 3, 2]]           # 6-P4/16
  - [-1, 4, A2C2f, [512, True, 4]]       # 7

  # P4 SharedExpertMoE (复用 "p3_p4" pool)
  - [-1, 1, SharedExpertMoE, [512, 4, 2, 0.5, 8, 1.2, 0.5, 1.0, 1.0, 0.01, 8, 2, 0.5, "p3_p4"]]  # 8

  - [-1, 1, Conv, [1024, 3, 2]]          # 9-P5/32
  - [-1, 4, A2C2f, [1024, True, 1]]      # 10
  # 注意: P5 不使用 MoE (轻量化设计)

# YOLO-Master-v0.8-MoT head (与 v08_mot 一致)
head:
  # P5 → P4
  - [-1, 1, nn.Upsample, [None, 2, "nearest"]]
  - [[-1, 8], 1, Concat, [1]]            # cat backbone P4
  - [-1, 2, C2fMoT, [512, 2, 8, 2, 7, 4, 2.0, 1.0, 0.01, 0.5]]   # 13

  # P4 → P3
  - [-1, 1, nn.Upsample, [None, 2, "nearest"]]
  - [[-1, 5], 1, Concat, [1]]            # cat backbone P3
  - [-1, 2, C3k2, [256, True]]           # 16 (P3 浅层, 与 v08_mot 一致)

  # P3 → P4 bottom-up
  - [-1, 1, Conv, [256, 3, 2]]
  - [[-1, 13], 1, Concat, [1]]           # cat head P4
  - [-1, 2, C2fMoT, [512, 2, 8, 2, 7, 4, 2.0, 0.8, 0.01, 0.5]]   # 19

  # P4 → P5 bottom-up
  - [-1, 1, Conv, [512, 3, 2]]
  - [[-1, 10], 1, Concat, [1]]           # cat backbone P5
  - [-1, 2, C2fMoT, [512, 2, 8, 2, 7, 4, 2.0, 0.8, 0.01, 0.5]]   # 22

  - [[16, 19, 22], 1, Detect, [nc]]      # Detect(P3, P4, P5)
```

##### 方案 B：激进型（Backbone + Head 全 MoE/MoT 覆盖，论文未来工作）

**设计目标**：在 v08_mot 基础上，**backbone 增加 2 个 MoE 块、head 增加 2 个 C2fMoT 块**，验证"专家堆叠饱和点"

**与 v08_mot 的关键差异**：

| 元素 | v08_mot | 方案 B | 说明 |
|------|---------|--------|------|
| **backbone MoE 块** | 3 | **5** | +2（+67%）：在 P2/P3 浅层各加 1 个 MoE |
| **head C2fMoT 块** | 3 | **5** | +2（+67%）：P3/P3→P4 各加 1 个 C2fMoT |
| head P3 | C3k2 | **C2fMoT** | 强化 MoT 比例 |

| 训练时间 | 19.5h | ~26h | +6.5h（+33%）|
| 显存风险 | 3.5G | ~5G | 🟡 中等（接近 8GB 上限）|

##### 方案 C：分场景路由（MoE+MoA 混合 backbone + C2fMoT+C2fMoA 混合 head，论文未来工作）

**设计目标**：在 v08_mot 基础上，**backbone 引入 MoA 块、head 引入 C2fMoA 块**，验证多类型专家路由对不同尺度目标的适应性

**阶段 3：定位根因**（2026-07-28，阅读 `shared_expert_moe.py`）

发现 `SharedExpertMoE` 使用**类级别注册表**（class-level registry）：

```python
class SharedExpertMoE(nn.Module):
    _SHARED_POOLS = {}  # 类变量，所有实例共享

    def __init__(self, ..., pool_name="default"):
        if pool_name not in SharedExpertMoE._SHARED_POOLS:
            SharedExpertMoE._SHARED_POOLS[pool_name] = {...}
```

**根因分析**：
1. 类变量 `_SHARED_POOLS` 在 `__init__` 时被填充，但当模型从 CPU → GPU 时（`model.cuda()`），`_apply()` 方法只转移模型自身的参数，**不会转移 `_SHARED_POOLS` 字典中的 expert**
2. 前向推理时，expert 仍在 CPU（原始 device），而输入张量在 GPU，触发**隐式 device 转移**（每次推理都有 device transfer 开销）
3. warmup 阶段（前 50 次）包含 class-level registry 的 lazy initialization（PyTorch 第一次见到某个算子时会编译 CUDA kernel），耗时 >1s

**阶段 4：实施修复**（2026-07-28，三处修复）

```python
# 修复 1：在 SharedExpertMoE 中添加 reset_shared_pools() 类方法
@classmethod
def reset_shared_pools(cls):
    cls._SHARED_POOLS.clear()

# 修复 2：在 _apply() 中同步 device
def _apply(self, fn, recurse=True):
    super()._apply(fn, recurse)
    for pool_name, pool in self._SHARED_POOLS.items():
        for expert in pool['experts']:
            expert._apply(fn)
    return self

# 修复 3：在 benchmark 脚本入口强制 reset
SharedExpertMoE.reset_shared_pools()
```

#### 4.4.2 错误数据复盘表

| 测量轮次 | 方案 D GPU 延迟 | 状态 | 原因 |
|----------|----------------|------|------|
| 第 1 次（错误） | **245.310ms** | ❌ 错误 | SharedExpertMoE class-level registry 状态残留 + warmup=50 不够 |
| 第 2 次（错误） | ~150ms | ❌ 错误 | 部分修复但未彻底（仅增 warmup，未修复 `_apply`） |
| 第 3 次（正确） | **51.726ms** | ✅ 正确 | 修复 SharedExpertMoE（`_apply` + `reset_shared_pools`） + warmup=500 + reps=2000 |

#### 4.4.3 错误根因分析（`SharedExpertMoE` 实现缺陷）

1. **类级别注册表（class-level registry）残留状态**：`SharedExpertMoE` 用类变量 `_SHARED_POOLS` 缓存 expert pool，当模型在不同 device（CPU → GPU）切换时，旧 device 的状态未被清除
2. **`_apply` 方法未传播 device**：`nn.Module._apply()` 用于将模型转移到 device（CPU/GPU），但 `SharedExpertMoE` 重写时未正确处理 `_SHARED_POOLS` 的 device 同步
3. **warmup 不足**：前 50 次推理（前 50 reps）包含 class-level registry 的 lazy initialization，导致前几次推理耗时极高（>1s），拉高 `mean` 统计

#### 4.4.4 修复方法（`ultralytics/nn/modules/moe/shared_expert_moe.py`）

```python
# 1. 在 SharedExpertMoE 中添加 reset_shared_pools() 方法
@classmethod
def reset_shared_pools(cls):
    cls._SHARED_POOLS.clear()

# 2. 在 _apply() 中同步 device
def _apply(self, fn, recurse=True):
    super()._apply(fn, recurse)
    for pool_name, pool in self._SHARED_POOLS.items():
        # 将 pool 的所有参数转移到新 device
        for expert in pool['experts']:
            expert._apply(fn)
    return self

# 3. 在 benchmark 前强制 reset
SharedExpertMoE.reset_shared_pools()
```

#### 4.4.5 经验总结

1. **GPU Benchmark 必须 warmup ≥ 500**：消除 CUDA kernel lazy initialization 和 class-level registry 的初始化开销
2. **类级别状态（class-level state）必须跟随 device 切换**：`_apply()` 方法是 PyTorch 标准的 device 同步钩子，必须正确实现
3. **首次测量结果不可信**：任何架构创新（特别是 MoE/MoT/共享专家池）首次 GPU 测量都应重复 3 次以上，确认数据稳定
4. **`latency_ms_min` vs `latency_ms_mean`**：245ms 的 min 仍达 35.420ms（修复前数据），说明不是单次抖动，而是持续性问题，必须查根因而非简单增大 warmup

#### 4.4.6 对方案 D 的影响

- 修复前 245ms 看起来方案 D 比 MoT 基线（42.15ms）慢 481%，**几乎判定方案失败**
- 修复后 51.726ms 比 MoT 基线（52.735ms）**还快 1.9%**
