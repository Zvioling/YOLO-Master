## 2. 项目一：ES-MoE 自适应推理优化训练

### 2.1 原文摘录

**项目名称**：基于 ES-MoE 的自适应推理优化训练

**核心目标**：基于 YOLO-Master 的 ES-MoE（Efficient Sparse Mixture-of-Experts）架构，针对特定应用场景设计并优化自适应推理策略，实现计算资源的动态分配。

**适用场景**：实时视频监控系统（空旷走廊 vs 拥挤商场的算力差异分配）。

---

### 2.2 四大核心技术要点

| # | 技术要点 | 核心挑战 | 解决思路 |
|---|---------|---------|---------|
| 1 | **动态路由网络设计** | 路由计算开销与精度的平衡 | 深度可分离卷积替代标准卷积，**8× 激进下采样**降低 95% 路由 FLOPs |
| 2 | **Soft-to-Hard 策略切换** | 训练梯度连续性 vs 推理计算稀疏性 | 训练 Soft Top-K 保梯度，推理 Hard Top-K 真稀疏 |
| 3 | **负载均衡损失调优** | 防专家坍塌，确保各专家充分利用 | **Load Balancing Loss + Z-Loss** 组合，抑制过大 Logits |
| 4 | **专家专业化设计** | 不同专家需学习互补视觉特征 | 利用 **3×3/5×5/7×7** 不同感受野构建多尺度专家组 |

### 2.3 模型配置要求（原文 §1.3）

| 配置项 | 要求 |
|--------|------|
| **基础模型** | `Tencent/YOLO-Master/ultralytics/cfg/models/master/v0_1/det/yolo-master-n.yaml`（含 `ModularRouterExpertMoE`） |
| **可调参数** | `ES_MOE`/`ModularRouterExpertMoE` 层（专家数量 4-8 个，激活数量 1-2 个） |
| **数据集** | VisDrone（小目标）或 SKU-110K（密集场景） |
| **环境** | PyTorch ≥ 2.0，CUDA ≥ 11.8 |

> **仓库差异说明**：原文 §1.3 指明 `v0_1/det/yolo-master-n.yaml`，但仓库里 `v0/det/yolo-master-n.yaml` 和 `v0_1/det/yolo-master-n.yaml` 同时存在，两者结构类似；项目实际**推荐使用 `v0/det/yolo-master-esmoe-n-visdrone.yaml`**（仓库原生 ES-MoE YAML，10 类 VisDrone，4 个 ES_MOE 层 × 3 专家 = 12 个专家节点），原文中 §1.3 的"v0_1"路径仅是仓库的命名漂移。

### 2.4 训练要求（原文 §1.3）

- 实现自定义路由可视化工具（监控各专家激活频率）
- 调整负载均衡损失权重（默认 0.01），观察专家利用率变化
- 对比不同 Top-K 策略（K=1/2/3）的精度-延迟权衡
- 实现动态批处理策略（根据输入图像复杂度自适应调整批大小）

### 2.5 五大验收项（原文 §1.4）

| # | 验收项 | 通过标准 | 优秀标准 |
|---|--------|---------|---------|
| 1 | **基础功能** | 成功训练 + 推理流程 | 训练过程稳定，无梯度爆炸或 NaN |
| 2 | **专家利用率** | 各专家差异 < 30% | 差异 < 15%，无闲置专家 |
| 3 | **性能指标** | VisDrone mAP ≥ 38% / SKU-110K mAP ≥ 55% | VisDrone mAP ≥ 40% / SKU-110K mAP ≥ 57% |
| 4 | **推理效率** | 相比基线模型延迟 ↓ ≥ 10% | 延迟 ↓ ≥ 20%，精度损失 < 0.5% |
| 5 | **可视化分析** | 专家激活热力图 | 场景复杂度与专家选择的关联分析 |

> **注**：原文中 VisDrone mAP 阈值（38-40%）是按 COCO 预训练微调的经验值。本项目 `experiments_zviolin/runs/esmoe_v0_k2-2` 的 100 epoch 实测 mAP50-95 为 **17.27%**（epoch 100, time=46842s）。该差距源自 VisDrone 数据集"航拍密集小目标"的固有难度 + RTX 5060 8GB 显存下 batch 只能调到 4，因此本项目的**对照基线**是 `v084`（MoE 基线，mAP50-95=16.84%），ES-MoE 相对基线 **+0.43%**（精度增益有意义），参见 [04-任务1-ES-MoE训练.md](./04-任务1-ES-MoE训练.md) §1.3。

### 2.6 学习目标（原文 §1.5）

- 稀疏计算范式：理解 MoE 架构的设计原理与实现细节
- 训练稳定性技巧：处理负载均衡、梯度流动等 MoE 训练问题
- 性能权衡分析：在精度、延迟、计算量之间进行系统权衡
- 可视化调试能力：通过专家激活模式诊断模型行为

## 3. 项目二：LoRA 参数高效微调的多场景应用

### 3.1 原文摘录

**项目名称**：LoRA 参数高效微调的多场景应用

**核心目标**：基于 YOLO-Master 的 LoRA 支持，设计多场景迁移学习方案，实现"一基座多任务"的高效部署模式。

**适用场景**：高校实验室与中小企业的资源受限场景（全量微调需数十GB显存，LoRA 仅需 10% 可训练参数 + 70% 显存节省）。

---

### 3.2 四大核心技术要点

| # | 技术要点 | 核心挑战 | 解决思路 |
|---|---------|---------|---------|
| 1 | **LoRA 秩与缩放因子选择** | 秩 r 过大增加计算量，过小表达能力不足 | 实验确定 r ∈ [8, 32]、alpha ∈ [16, 64] 的最优组合 |
| 2 | **多任务 Adapter 管理** | 不同任务间知识干扰与遗忘问题 | 设计任务特定的 LoRA 权重，支持动态切换与组合 |
| 3 | **数据稀缺场景适配** | 目标域标注数据极少时的有效学习 | 结合数据增强与伪标签技术 |
| 4 | **推理时延控制** | LoRA 引入的额外计算开销 | 采用权重合并技术，推理时将 Adapter 融入基座权重 |

### 3.3 模型配置要求（原文 §2.3）

| 配置项 | 要求 |
|--------|------|
| **基座模型** | YOLO-Master-N 预训练权重（COCO 数据集） |
| **数据集** | 3 个任务（BDD100K 交通 / NEU-DET 工业 / SKU-110K 零售） |
| **LoRA 参数** | lorar=16, loraalpha=32 |
| **环境** | PyTorch + PEFT 库（第三方） |

> **仓库差异说明**：仓库里**没有**独立的"LoRA"模块，但存在 `ultralytics/nn/peft/molora/`（MoLoRA）—— 这是一个与 PEFT-LoRA 完全不同的内部实现。原 §2.3 提到的 `lorar=16, loraalpha=32` 是 PEFT 库的语义，在 YOLO-Master 里对应 `molora_r=16, molora_alpha=32`。

### 3.4 训练要求（原文 §2.3）

- 修改训练配置启用 LoRA（lorar=16, loraalpha=32）
- 实现 Adapter 保存与加载机制（支持多版本管理）
- 对比全量微调与 LoRA 微调的性能差距
- 设计动态任务切换接口（根据输入类型自动选择对应 Adapter）
- 实现 Adapter 权重可视化
- 探索 Adapter 融合技术

### 3.5 五大验收项（原文 §2.4）

| # | 验收项 | 通过标准 | 优秀标准 |
|---|--------|---------|---------|
| 1 | **基础功能** | 成功完成 3 个任务的 LoRA 微调 | 训练过程稳定，无过拟合 |
| 2 | **性能指标** | 各任务 mAP 达到全量微调的 90% | 达到 95% 以上，部分任务超越全量微调 |
| 3 | **资源效率** | 可训练参数 < 15%，显存节省 ≥ 60% | 可训练参数 < 10%，显存节省 ≥ 70% |
| 4 | **多任务切换** | 支持 3 个任务的动态切换 | 切换延迟 < 100ms，支持任务组合推理 |
| 5 | **可解释性** | 提供 Adapter 权重分布分析 | 可视化不同任务的关注区域差异 |

### 3.6 学习目标（原文 §2.5）

- PEFT 技术体系：深入理解 LoRA 原理
- 多任务学习策略：掌握 Adapter 管理、任务切换
- 资源受限优化：有限算力下最大化性能
- 领域适配能力：通用检测模型快速适配垂直领域

### 3.7 与 YOLO-Master 仓库匹配度

| 项目要求 | YOLO-Master 仓库对应 | 匹配度 |
|---------|---------------------|--------|
| LoRA 模块 | ⚠️ 仓库无 PEFT-LoRA 实现，但有 `MoLoRA`（`ultralytics/nn/peft/molora/`） | 🟡 **30%**（语义不完全等价） |
| 多任务 Adapter 管理 | ⚠️ 需自实现 Adapter 切换逻辑 | 🔴 **0%** |
| 数据集 | ⚠️ 需下载 BDD100K/NEU-DET/SKU-110K | 🟡 **30%** |
| 权重合并技术 | ⚠️ MoLoRA 有 adapter 合并支持 | 🟡 **50%** |
| 动态任务切换 | ❌ 需自实现 | 🔴 **0%** |

## 4. 项目三：模型剪枝与端侧部署实践

### 4.1 原文摘录

**项目名称**：模型剪枝与端侧部署实践

**核心目标**：完成从模型诊断、智能剪枝到端侧部署的完整工程链路，构建生产级推理系统。

**适用场景**：移动端 AI 应用（智能相机、无人机巡检、AR 眼镜）。

---

### 4.2 四大核心技术要点

| # | 技术要点 | 核心挑战 | 解决思路 |
|---|---------|---------|---------|
| 1 | **专家利用率诊断** | 准确识别冗余专家，避免误剪 | 基于验证集统计各专家激活频率，设置自适应阈值 |
| 2 | **结构化剪枝策略** | 剪枝后模型结构变化的部署兼容性 | 采用通道剪枝而非权重剪枝，保持网络拓扑完整 |
| 3 | **量化与图优化** | INT8 量化精度损失与推理速度平衡 | 使用 TensorRT PTQ/QAT，校准敏感层保留 FP16 |
| 4 | **跨平台部署适配** | Android 端算力受限与异构计算 | ncnn 框架优化，利用 GPU/Vulkan 加速推理 |

### 4.3 模型配置要求（原文 §3.3）

| 配置项 | 要求 |
|--------|------|
| **剪枝工具** | `Tencent/YOLO-Master/ultralytics/nn/modules/moe/pruning.py::MoEPruner` |
| **剪枝阈值** | 默认 15%（剔除利用率 < 15% 的专家） |
| **部署框架** | TensorRT（GPU 端）+ ncnn（Android 端） |
| **数据集** | VisDrone/COCO（已配置） |

### 4.4 训练要求（原文 §3.3）

- 使用 MoEPruner 工具进行专家利用率诊断
- 在验证集上收集专家使用统计，生成利用率分布直方图
- 设置剪枝阈值，自动剔除低利用率专家
- 对比剪枝前后的参数量、FLOPs、mAP
- 实现渐进式剪枝策略
- 导出 ONNX + TensorRT 优化（FP16/INT8）
- 导出 ncnn + Vulkan 加速（Android）
- 设计推理服务 API（图片/视频流）
- 实现延迟监控与自适应批处理

### 4.5 五大验收项（原文 §3.4）

| # | 验收项 | 通过标准 | 优秀标准 |
|---|--------|---------|---------|
| 1 | **基础功能** | 成功执行 MoEPruner 剪枝，完成 TensorRT 导出 | 剪枝过程自动化，支持批量处理 |
| 2 | **剪枝效果** | 参数量 ↓ ≥ 20%，mAP 损失 < 1% | 参数量 ↓ ≥ 30%，mAP 损失 < 0.5% |
| 3 | **推理加速** | TensorRT FP16 延迟 ↓ ≥ 25% | INT8 延迟 ↓ ≥ 40%，精度损失 < 1% |
| 4 | **端侧部署** | Android 端成功运行，单帧 < 200ms | 单帧 < 100ms，支持实时视频流 |
| 5 | **系统完整性** | 提供完整部署文档与性能基准 | 提供 Docker 镜像与一键部署脚本 |

### 4.6 学习目标（原文 §3.5）

- 模型压缩技术：剪枝、量化、知识蒸馏
- 部署优化能力：从训练到生产的端到端工程实现
- 性能 profiling：熟练使用各类工具进行延迟分析
- 跨平台开发：移动端 AI 部署的特殊考量
