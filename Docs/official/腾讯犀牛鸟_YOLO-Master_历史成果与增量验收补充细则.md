# **1. 制定目的与适用原则**

本细则用于区分“锁定前已经存在的成果”与“本轮实战周期新增贡献”，避免把已有功能重复包装为从零开发，同时确保不同课题、不同团队的起点与奖励口径一致。

承认历史贡献：既有代码、实验和报告继续保留原作者署名、贡献记录与复用价值。

不重复计分：锁定前已公开、已合并或已形成完整结论的成果，不直接兑换本轮
P1/P2。

只评真实增量：P1/P2 重点评价锁定后的机制、工程、产品、实验或分析增量。

规则统一适用：A3 与其他课题采用同一套基线、举证、diff 和成员归属规则。

不针对个人：本细则处理的是成果状态和证据边界，不对任何个人既往贡献作负面评价。

# **3. 个人 fork 与历史成果登记**

除上述两个公共仓库外，其他个人 fork
不进入统一公共基线清单。参与者如主张锁定前已有成果，应自行完成一次性登记；登记的作用是划清既有成果，不是为既有成果追加本轮分数。

## **3.1 登记时限与最低字段**

登记截止：2026-08-25 23:59:59（UTC+8）。截止后不得通过更换基线
SHA、改写历史或补报旧报告来扩大“历史成果”范围。

| **字段** | **填写要求** |
|----|----|
| 课题与成员 | 课题编号、Owner、全部成员及各自职责 |
| 仓库 | 公开可访问的 repository URL、默认分支 |
| 个人基线 | 锁定前 HEAD 的完整 40 位 commit SHA 与固定 commit URL |
| 既有成果范围 | 按文件、模块、后端、数据集和结论逐项列出，不写笼统描述 |
| 历史报告 | 报告 URL/文件版本、生成日期、原始日志或 release/PR/issue 证据 |
| 拟新增工作 | 计划在锁定后完成的代码、实验、分析和预期 PR |

## **3.2 可接受与不可接受的证据**

可接受：公开 commit 页面、锁定前已存在的
PR/Issue/Release、带版本的报告、可复现配置、原始日志和产物校验值。

建议：为个人基线创建不可移动的 tag，例如
rhino-2026-0821-baseline，并在登记表中同时填写 tag 与 SHA。

不可单独作为证据：作者日期、口头说明、后补
README、截图、无法访问的私有仓库或只有结论没有原始记录的报告。

私有成果确需备案时，应在截止前向导师提供只读访问或不可变归档；否则统一按未备案处理。

登记后禁止 force-push
改写相关历史；确有技术原因时须保留原始对象并书面说明。

## **3.3 未登记的处理**

未在截止前登记的个人既有成果仍可被团队复用，也保留原作者历史署名，但不得在结项时临时主张为本轮新增
P1/P2。验收只认可公共基线之后、且能够由 PR、Issue、commit
和实验记录证明的新增工作。

# **4. 增量验收方法**

结项时锁定 FINAL_REF，并以“基线状态 →
最终状态”的差异作为主要证据。评审不只看代码行数，而是同时检查代码、实验与知识结论三个层面的新增量。

| **增量层** | **主要证据** | **典型有效贡献** |
|----|----|----|
| 代码增量 | BASE_REF→FINAL_REF diff、PR、测试 | 新机制、新后端、新兼容层、缺陷修复 |
| 实验增量 | 配置、manifest、原始日志、指标表 | 新增架构/数据/量化口径、消融、失败复现 |
| 知识增量 | 分析报告、判读标准、证据链 | 原因定位、边界结论、负结果、go/no-go 建议 |

## **4.1 P0 / P1 / P2 计分边界**

Smoke：可直接使用历史成果证明环境、能力与最小链路，但必须在锁定版本上重新执行。

P0：历史功能经当前版本复现、校准并形成完整证据后可以满足；仅引用旧
README 不算完成。

P1：必须存在锁定后的实质新增；原则上至少具备“代码增量或实验增量”之一，并形成新的可判读结论。

P2：必须超出原有能力边界，形成跨架构/跨后端矩阵、机制分析、自动化工具、性能恢复或高质量负结果。

重复运行：只重跑原表格、重排旧报告或将已有代码迁移目录，不单独构成
P1/P2。

## **4.2 推荐核验命令**

代码状态差异：git diff \<BASE_REF\> \<FINAL_REF\>

新增提交集合：git log --reverse \<BASE_REF\>..\<FINAL_REF\>

基线可达性：git merge-base --is-ancestor \<BASE_REF\> \<FINAL_REF\>

若个人 fork 与官方仓库已分叉，须补充 merge-base、cherry-pick
来源与上游同步说明，避免将上游已有提交计为个人新增。

# **5. A3 专项解释**

A3 参考仓库在锁定前已具有跨平台 runner、ONNX/NCNN/MNN 对齐、EsMoE 混合
INT8、技术报告、mixture export driver 以及多种 mixture
的跨后端兼容。这些内容统一作为 A3 公共参考
baseline，不重复认定为本轮新增 P1/P2。

| **等级** | **本轮建议认定口径** |
|----|----|
| Smoke / P0 | 在锁定的 YOLO-Master 版本上重新复现部署链路，提交环境、命令、成功/失败日志与精度差；验证历史结论是否仍适用。 |
| P1 | 新增至少一个非 EsMoE 路由族（优先 MoT）的真实 FP32/FP16/INT8 闭环，接入统一 validation harness，并提交精度、时延、体积、失败算子和一次路由漂移分析。 |
| P2 | 完成五族统一量化矩阵、FP32/INT8 专家选择一致率、自动敏感层回退、QAT 精度恢复或真实端侧验证中的至少两项。 |

| **关键区分：**“能够导出某个 mixture”不等于“完成该架构的量化验证”；新增贡献必须给出锁定后新增的量化、评测、路由行为或恢复机制证据。 |

# **6. 团队成员贡献归属**

团队可以共享 baseline、脚手架、GPU
和数据，但每位成员必须拥有可追溯的主要工作包。无需机械要求“一人一个
PR”，但不接受仅在报告署名、没有可核验产出的挂名贡献。

每个工作包明确 Owner、范围、目标等级、Issue/PR、实验编号与最终证据。

每位成员至少提供一种主要产物：代码
PR、实验包、分析工具、复现测试或独立报告章节。

共同完成的工作可联合署名，但须说明每人的具体职责和可复核贡献。

团队至少提交一个可审查的集成 PR 或等价开源交付。

# **7. 例外、争议与执行**

唯一常规例外：锁定前已有书面备案，且备案材料明确约定该成果属于本轮工作。

发生基线不一致、历史改写或贡献归属争议时，以公开对象时间、PR/Issue
记录、原始日志和导师备案为准。

无法确认是否属于新增时，默认按 baseline
处理；允许补充证据，但不允许补造时间线。

本细则与课题任务书冲突时，以本细则关于历史成果、基线锁定和新增 diff
的条款为准；其他验收要求不变。

建议在 8 月 24 日准入检查完成后关闭基线登记，并在课题登记表中固化
BASE_REF、Owner 和工作包。
