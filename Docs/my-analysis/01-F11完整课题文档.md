## §0 一页读懂

推荐流程:个人提交第一、第二、第三志愿;导师按志愿顺序、技能匹配、课题容量、算力与团队结构撮合。组队后锁定一个主选题和一个备选/降级方向。8 月 24 日通过准入检查后进入完整实验;未通过则限时补齐、缩小范围或切换备选。

| **阶段** | **时间** | **必须发生的结果** |
|----|----|----|
| 筹备与登记 | 8.14–8.23 | 三志愿、团队意向、技能/算力/数据登记;代码环境与最小 smoke |
| 准入门槛 | 8.24 | Owner、commit、baseline、P0、复现命令、GPU/数据路径均明确 |
| Sprint 1 | 8.25–8.31 | 最小功能闭环;首轮 on/off 或 baseline/改进数字 |
| Sprint 2 | 9.1–9.7 | 关键消融;中期演示;PR 草稿与测试开始 |
| 收敛与交付 | 9.8–9.12 | 多 seed/补实验;文档、测试、已知局限 |
| 结项 | 9.13–9.14 | 冻结结果;答辩;提交 PR/报告/复现包 |

### P0 / P1 / P2 与计划标准的关系

P0(准入与保底):必须完成,否则课题不达标。可近似理解为官网"通过标准"的最低可验证部分,但最终仍以官方计划评审规则为准。

P1(预期完成):本课题正常结项的主要目标。可作为"优秀标准"的核心参照,但不是自动获得优秀评价的充分条件。

P2(理想目标):超额贡献、机制分析、跨任务泛化、正式发布等加分项,用于冲击优秀/激励提名。

**重要:P0/P1/P2 是项目内部任务分级,不替代腾讯犀牛鸟官网最终评审口径。**

## §1 仓库事实与共同技术边界

仓库定位是面向实时目标检测的 YOLO-style 框架,核心是 ES-MoE 与动态路由;当前主页同时列出 MoA、MoT、LoRA/YOLO-PEFT、Agent Skill、诊断剪枝、Sparse SAHI、CW-NMS 与部署能力。

不要把 README 中已有的功能写成"从零开发"。课题应明确属于:补齐闭环、修复缺口、严谨复测、扩展任务、工具化或产品化。

所有代码位置引用必须在锁定 commit 后重新搜索与验证;不要沿用旧文档中的绝对行号。

新增辅助损失或路由类型时,必须验证训练总损失实际收到该项,并用单测或非零日志证明;不能只看配置键存在。

动态路由导出必须显式处理不支持、拒绝或 sparse→dense fallback;不允许静默改变模型语义。

WebUI 统一复用 Agent Skill/dispatcher 执行,不直接拼接任意 shell。

### 统一实验红线

| **红线** | **最低要求**                                     |
|----------|--------------------------------------------------|
| 版本     | 记录 tag/commit、环境、依赖与配置路径            |
| 对照     | 同数据、同预算、同增广、同评测口径               |
| 统计     | 提升/下降原则上≥3 seed;否则显式声明单 seed 局限 |
| 负结果   | 允许,但必须提前定义判读线并给出证据链           |
| PR       | 改动摘要、测试证据、消融数据、已知局限四节齐全   |
| 安全     | 数据许可、路径白名单、日志脱敏、无任意 shell     |

### 2.1 D1 / D2 / F11 的边界必须先讲清

**三题可以共享同一套冻结教师特征和缓存,但研究对象不同。开题时若无法用一句话说明"教师信号进入哪里",不得同时登记多个题名来规避边界。**

| **课题** | **教师信号进入位置** | **主要训练对象** | **核心判据** | **推理阶段教师** |
|----|----|----|----|----|
| D1 冻结适配 | 作为检测器输入特征 | Latent Mixture + 检测头 | 成本—精度收益 | 不需要 |
| D2 表征 KD | 学生 backbone 中间层 | backbone / 投影层 | 学生特征与任务指标 | 移除 |
| **F11 路由 KD** | **Router 的软目标分布** | **router/gate** | **路由稳定性、负载与任务指标** | **移除** |

### F11 教师软目标的最低合法定义

> 📌 **F11 相关**:此节直接约束 F11

不能直接把 DINO patch 特征当作专家编号;两者语义空间不同。

建议以"各专家输出与教师特征的一致性"或"各专家对当前样本/token 的效用"形成 q_teacher,并记录温度、平滑和置信度掩码。

必须证明 q_teacher 不是恒定均匀分布或单专家坍塌,并对比无 KD、表征 KD 和 Router KD。

训练期可计算全部专家形成教师目标;推理期必须恢复学生稀疏路由,不保留教师模型。

## §5 统一汇报与 PR 模板

### 双周/中期汇报(建议 5 页)

问题与假设:一句话说明要验证什么。

当前 commit、数据、预算、对照与复现命令。

已完成证据:可运行链路、数字、曲线、截图或失败日志。

结论与不确定性:哪些已被证实,哪些仍不能判断。

下一阶段、风险触发线与所需协作。

### PR 描述四节

改动摘要:改了什么、为何改。

测试证据:命令、环境、单测/集成测试结果。

消融数据:同预算对照、seed、统计口径。

已知局限:不支持范围、fallback、性能开销与后续工作。

### 复现包最低目录

configs/(训练与评测配置) · scripts/(入口命令) · results/(机器可读结果) · env/(依赖与硬件) · README.md(从零复现) · limitations.md(已知局限)

### 结项评分建议(内部参考)

| **维度**       | **权重** | **判定重点**             |
|----------------|----------|--------------------------|
| P0 完整性      | 35%      | 能运行、能复现、证据闭环 |
| P1/P2 技术贡献 | 25%      | 机制、工程或产品增量     |
| 实验严谨性     | 20%      | 对照、seed、统计、负结果 |
| 开源质量       | 15%      | 测试、文档、PR 可维护性  |
| 协作与表达     | 5%       | 共享接口、汇报、答辩     |

## §A1 制定目的与适用原则

本细则用于区分"锁定前已经存在的成果"与"本轮实战周期新增贡献",避免把已有功能重复包装为从零开发,同时确保不同课题、不同团队的起点与奖励口径一致。

承认历史贡献:既有代码、实验和报告继续保留原作者署名、贡献记录与复用价值。

不重复计分:锁定前已公开、已合并或已形成完整结论的成果,不直接兑换本轮 P1/P2。

只评真实增量:P1/P2 重点评价锁定后的机制、工程、产品、实验或分析增量。

规则统一适用:A3 与其他课题采用同一套基线、举证、diff 和成员归属规则。

不针对个人:本细则处理的是成果状态和证据边界,不对任何个人既往贡献作负面评价。

## §A4 增量验收方法

结项时锁定 FINAL_REF,并以"基线状态 → 最终状态"的差异作为主要证据。评审不只看代码行数,而是同时检查代码、实验与知识结论三个层面的新增量。

| **增量层** | **主要证据** | **典型有效贡献** |
|----|----|----|
| 代码增量 | BASE_REF→FINAL_REF diff、PR、测试 | 新机制、新后端、新兼容层、缺陷修复 |
| 实验增量 | 配置、manifest、原始日志、指标表 | 新增架构/数据/量化口径、消融、失败复现 |
| 知识增量 | 分析报告、判读标准、证据链 | 原因定位、边界结论、负结果、go/no-go 建议 |

### §4.1 P0 / P1 / P2 计分边界

**Smoke**:可直接使用历史成果证明环境、能力与最小链路,但必须在锁定版本上重新执行。

**P0**:历史功能经当前版本复现、校准并形成完整证据后可以满足;仅引用旧 README 不算完成。

**P1**:必须存在锁定后的实质新增;原则上至少具备"代码增量或实验增量"之一,并形成新的可判读结论。

**P2**:必须超出原有能力边界,形成跨架构/跨后端矩阵、机制分析、自动化工具、性能恢复或高质量负结果。

重复运行:只重跑原表格、重排旧报告或将已有代码迁移目录,不单独构成 P1/P2。

### §4.2 推荐核验命令

- 代码状态差异:`git diff <BASE_REF> <FINAL_REF>`
- 新增提交集合:`git log --reverse <BASE_REF>..<FINAL_REF>`
- 基线可达性:`git merge-base --is-ancestor <BASE_REF> <FINAL_REF>`

若个人 fork 与官方仓库已分叉,须补充 merge-base、cherry-pick 来源与上游同步说明,避免将上游已有提交计为个人新增。

每个工作包明确 Owner、范围、目标等级、Issue/PR、实验编号与最终证据。

每位成员至少提供一种主要产物:代码 PR、实验包、分析工具、复现测试或独立报告章节。

共同完成的工作可联合署名,但须说明每人的具体职责和可复核贡献。

团队至少提交一个可审查的集成 PR 或等价开源交付。

# 第四部分 · 任务书 F11 章节 原文(完整)

> 来源:任务书 §2.1 F11 章节(完整复制)

**主题 D｜基础模型与路由蒸馏 · F11**

**Foundation 路由 KD:DINO 教师 → YOLO-Master Router**

| **难度/性质**      | **算力** | **团队** |
|--------------------|----------|----------|
| 探索型｜高研究价值 | 中高     | 2–3 人   |

## 背景与核心问题

基础模型本身没有可直接复制的 YOLO-Master 专家路由,因此本题不能把 DINO 特征简单称为"路由标签"。课题需要先构造可信的教师软目标:将冻结 DINO patch 特征与各专家输出对齐,按特征一致性或专家效用形成教师分布 q_teacher,再用 KL/JS 等损失蒸馏学生 Router。核心问题是:基础模型的语义结构能否让路由更稳定、更均衡,并在推理时完全移除教师、保持零额外教师开销。

## 目标分级

**P0｜保底:** 完成最小路由 KD 闭环:缓存冻结教师特征;在单个路由层、2 个专家的小配置上生成非退化 q_teacher;KD loss 能反传到 Router 且任务 loss 正常下降。

**P1｜预期:** 完成 baseline / backbone 特征 KD / Router KD 同预算对照;报告 mAP、top-k 路由一致率、JS/KL、路由熵、专家负载、吞吐与显存,并证明教师在推理阶段完全移除。

**P2｜理想:** 扩展到多层或 MoE/MoT 两类路由;验证小样本或跨域泛化;比较 DINOv2/DINOv3 教师,或分析负结果来自教师软目标质量、专家同质化、温度/权重或路由坍塌。

## 8.24 准入检查

100 张图教师特征缓存可复现;单 batch 生成 q_teacher 且熵不接近 0/均匀常数;Router KD 梯度非零;提交一条训练命令、loss 日志、路由分布图和显存估算。

## 仓库切入点

各族 router/gate 的 logits 与 top-k 出口;routing snapshot / diagnose_model;训练 criterion 与 aux loss 注入;教师特征 hook、token/尺度对齐与投影层。新增 distill kind 必须显式注册或走独立 criterion,并以单测证明进入总 loss。

## 数据与环境

COCO mini 起步,可加 VisDrone/工业小数据检验小样本与跨域;教师特征优先离线缓存。单卡 24G 可做最小验证,多层/多专家消融需协调更多 GPU 时。

## 本题冲刺计划

| **时间**  | **目标**                                               |
|-----------|--------------------------------------------------------|
| 8.22–8.23 | 锁定 commit;读切入点;跑准入 smoke;确认主/备路线     |
| 8.24      | 现场检查:命令、日志、配置、Owner、P0 与降级方案       |
| 8.25–8.31 | 完成最小闭环与首轮数字;每日保留可运行 checkpoint/测试 |
| 9.1–9.7   | 关键消融与中期演示;PR 草稿;补单测与文档              |
| 9.8–9.12  | 多 seed/补实验;风险收敛;冻结复现包                   |
| 9.13–9.14 | 结项答辩;提交最终 PR、报告与已知局限                  |

## 交付物与验收证据

路由 KD 设计文档;教师软目标与缓存工具;Router KD 模块 PR;三方同预算对照表;路由行为图;推理零教师依赖证明;go/no-go 建议。

## 风险与降级

教师软目标退化时先做温度、平滑与置信度掩码;专家输出不可比时增加共享投影;训练不稳时使用 λ warmup。若方法无效,降级为"教师语义结构与现有路由相关性审计",但必须保留量化证据。

## 建议学习顺序

先跑官方 quick start / Agent Skill smoke,确认环境与数据。
再读切入点源码和相关测试,画出输入—输出—损失/产物链。
先做最小 on/off 对照,再扩数据、seed 或界面;不要反向。
